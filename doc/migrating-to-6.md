# Migrating to dart-pdf 6.0

6.0 moves `dart_pdf_editor` and `dart_pdf_printing` from
`package:flutter/material.dart` to
[`material_ui`](https://pub.dev/packages/material_ui) (and `cupertino_ui`),
the packages Flutter's Material and Cupertino libraries are moving to.
material_ui is a copy, not a re-export: its `Theme`, `ThemeData`,
`ColorScheme`, `MaterialLocalizations`, `ScaffoldMessenger`, `TextField`,
`InputDecoration` and the rest are **different types** from the legacy ones
with the same names. Only widgets-layer values (`Color`, `TextStyle`,
`IconData`, `IconThemeData`, `Navigator`, `Overlay`, ...) are shared.

Most apps need no code changes beyond removing APIs deprecated in 5.x. Your
app can stay on `package:flutter/material.dart` for now; the editor bridges
to it. Moving the app to material_ui as well is what Flutter recommends, and
it is a mechanical `dart fix` (below).

## Requirements

- Flutter **3.47.0** or newer (`flutter: '>=3.47.0'`, material_ui 1.4's
  floor). The Dart SDK constraint (`^3.5.0`) and the language version are
  unchanged.
- `uses-material-design: true` in your app's `pubspec.yaml`, as before: the
  stock chrome draws Material Icons.

```yaml
flutter:
  uses-material-design: true
```

## Removed APIs (deprecated in 5.x)

| Removed | Use instead |
|---|---|
| `PdfEditingPreferences.themeMode` (`ThemeMode`) | `themePreference` (`PdfThemePreference`), mapped in your app |
| `PdfDialogSubmit(child: someButton)` | `PdfDialogSubmit.action(onSubmit: ..., child: ...)` |
| `pdfSearchInputBorder` | `OutlineInputBorder(borderRadius: pdfSearchFieldBorderRadius)` |

`themePreference` is stored under the same key `themeMode` used, so saved
choices carry over. Map it in whichever `MaterialApp` you use:

```dart
MaterialApp(
  themeMode: switch (prefs.themePreference) {
    PdfThemePreference.system => ThemeMode.system,
    PdfThemePreference.light => ThemeMode.light,
    PdfThemePreference.dark => ThemeMode.dark,
  },
  ...
)
```

`PdfDialogSubmit.action` marks any widget as a `showPdfDialog` dialog's Enter
action; pass it the same callback the button runs:

```dart
PdfDialogSubmit.action(
  onSubmit: canSave ? save : null,
  child: FilledButton(onPressed: canSave ? save : null, child: Text(label)),
)
```

## Localizations: the delegate list

Register `PdfEditorLocalizations.delegates` in a material_ui app:

```dart
import 'package:dart_pdf_editor/dart_pdf_editor.dart';
import 'package:material_ui/material_ui.dart';

MaterialApp(
  localizationsDelegates: PdfEditorLocalizations.delegates,
  supportedLocales: PdfEditorLocalizations.supportedLocales,
  ...
)
```

It is the editor's delegate plus material_ui's
`GlobalMaterialLocalizations.delegates` - the Material strings, cupertino_ui's
Cupertino strings and the widgets strings. Use the plural `delegates`: the
iOS and macOS text-selection menus read the Cupertino strings, and without
them they fail.

`DartPdfEditorLocalizations.localizationsDelegates` is generated by
`flutter gen-l10n`, which still emits the **legacy** `flutter_localizations`
delegates. Keep using it in an app on the legacy `MaterialApp`; in a
material_ui app it gives material_ui nothing for most locales. The same goes
for your own app's generated list, so a material_ui app with its own bundle
adds material_ui's delegates after it. If a file also imports
`package:flutter_localizations`, give one of the two imports a prefix:
`GlobalMaterialLocalizations` exists in both libraries.

```dart
import 'package:material_ui/material_ui.dart';

localizationsDelegates: [
  ...AppLocalizations.localizationsDelegates, // legacy, from gen-l10n
  DartPdfEditorLocalizations.delegate,
  ...GlobalMaterialLocalizations.delegates,   // material_ui's
],
```

Registering the delegates is recommended, not required: the editor's widgets
install material_ui's and cupertino_ui's localizations for the ambient locale
whenever the host lacks them (English where they have no translation), so a
misconfigured list cannot crash the editor.

## Apps still on `package:flutter/material.dart`

They keep working, themed. `PdfViewer`, `PdfReader`, `PdfEditorView` and
`PdfComparisonView` wrap their content in `PdfMaterialHost`, which, under a
legacy `MaterialApp`, supplies a material_ui `Theme`, the material_ui and
cupertino_ui localizations and a transparent material_ui `Material`. The
editor's dialogs, sheets, menus and text-field context menus re-inject the
same inside their routes, so `showPdfDialog`, `showPdfTextPrompt` and the
other prompts also work when your app calls them from outside the editor.

The theme comes from your legacy `Theme` through a small bridge
(`lib/src/legacy/legacy_host_bridge.dart`, the only file in the library that
imports the legacy library):

- **Carried over:** every `ColorScheme` role (your exact `primary`, dark
  mode), the `TextTheme`, the `IconTheme`, `platform`, `visualDensity` and
  `useMaterial3`. The theme follows your app's theme changes.
- **Not carried over:** component themes (`FilledButtonThemeData`,
  `InputDecorationTheme`, `DialogTheme`, ...) and `ThemeExtension`s. To style
  the editor's chrome, use the editor's own tokens or wrap it in a material_ui
  `Theme`:

```dart
PdfEditorView(
  bytes: bytes,
  theme: const PdfEditorThemeData(
    primary: Color(0xFF00897B),   // seeds the chrome's colour scheme
    brightness: Brightness.dark,  // whatever the host theme says
  ),
)
```

- **Notices** (the editor's SnackBars, with Undo) go to your legacy
  `ScaffoldMessenger`, so they look like your app's own. Without a messenger
  of either kind they appear as a toast in the root overlay.

The bridge costs about 12 KB of web JavaScript. If no app that hosts the
editor uses the legacy library, compile it out:

```sh
flutter build web --dart-define=PDF_LEGACY_MATERIAL_BRIDGE=false
```

With the define off the build is byte-identical to one without the bridge
(`tool/check_legacy_bridge_dce.sh` checks this in CI), and the editor then
ignores a legacy host's theme and messenger. `kPdfLegacyMaterialBridge`
reports the setting.

When Flutter removes `package:flutter/material.dart`, the bridge goes away
in a minor release.

## Your own widgets inside the editor

Widgets you pass into the editor's slots (header parts, `toolbarTrailing`,
dock panels, presenter overrides) can come from either library. Two things
to know:

- A legacy widget that reads `Theme.of(context)` gets your legacy theme only
  if one is above the editor; the editor's own theme is a material_ui one.
- Ink splashes paint on the nearest `Material` of the same library. Give a
  legacy `InkWell` inside an editor surface its own legacy `Material` if its
  splash should show.

Text fields in your own dialogs that may run under a non-Material host should
pass `contextMenuBuilder: pdfTextContextMenu`; `PdfDropdown` replaces
`DropdownButton` there. `PdfDropdown.decoration` is now a material_ui
`InputDecoration`.

## Tests

- A test that imports `package:flutter/material.dart` finds **nothing** with
  type-based finders on editor widgets: `find.byType(TextField)` matches the
  legacy `TextField`, and the editor builds material_ui's. Find editor
  widgets by their `pdf-*` keys (stable API) or import material_ui in the
  test. `find.byTooltip` keeps working.
- Casting a found widget (`tester.widget<FilledButton>(...)`) needs the
  material_ui class.
- `Theme.of(context)` in a test reads whichever library you imported; the
  editor's chrome reads material_ui's.

## Moving your app to material_ui

```sh
dart fix --apply --code=migrate_design_widgets
```

rewrites `package:flutter/material.dart` and `package:flutter/cupertino.dart`
imports to `material_ui`/`cupertino_ui` and adds the dependencies (replace
the `any` constraints it writes). Then fix the delegate list as above (the
fix does not touch it) and check `export` directives by hand. Once nothing
in the app uses the legacy library, build with
`--dart-define=PDF_LEGACY_MATERIAL_BRIDGE=false`.
