# 2026-07-22 — cache decoded stream bytes in CosDocument (#392)

`CosDocument.decodeStreamData` re-ran the whole filter chain (and the cipher, on
encrypted files) on every call, and every consumer above pdf_cos decodes the
same streams repeatedly: a page's `/Contents` for render *and* text-extract *and*
element-enumeration *and* colour processing; form XObjects/appearances per use;
fonts, cmaps, functions.

## Change

A decoded-payload cache on `CosDocument`, keyed by `(CosStream identity,
stopBeforeFilter)`, checked at the top of `decodeStreamData`.

**Correct without invalidation.** A `CosStream`'s `rawBytes` and `dictionary`
are immutable for its lifetime, so its decoded bytes are stable; an edit that
changes content builds a *new* stream object (new identity → cache miss). Entries
for streams a revision redefined become unreachable and age out under the budget
- no explicit invalidation needed. The result is treated as read-only by every
caller: `decodeStream` already returns `CosStream.rawBytes` verbatim for an
unfiltered stream, so that contract predates this change - and an audit of all
~40 `decodeStreamData` consumers found none that writes into a decode result
(they parse it, copy it into a builder, or decode pixels from it).

**Bounded so it never competes with the decoded-image budget (#405).** A result
larger than `decodedStreamCacheItemCapBytes` (1 MB) is never cached - large
image / soft-mask planes are decoded a bounded number of times and their pixels
live in `PdfImageCache`, so caching their raw planes here would only crowd out
the small hot streams. The total is capped at `decodedStreamCacheBudgetBytes`
(16 MB) with LRU eviction (a plain `Map` is insertion-ordered: a hit reinserts
MRU, eviction drops the LRU front). Both are settable for memory-constrained
hosts.

## Scope note

#393 (parsed-ops cache) and #394 (recorded single-walk default) already removed
the *intra-render* double-decode this ticket originally headlined, so the value
now is **cross-consumer and cross-render**: the second consumer of a stream
(text extraction after render, element enumeration, a re-render on zoom) and
`#402`'s span-splicing follow-up, which needs the retained bytes to live
somewhere - this is that somewhere.

## Measured

`tool/perf.sh diff main dartpdf-corpus` (4 interleaved A/B runs; the sweep
decodes each page's `/Contents` once for `interpret` and again for `extract`):

```
extractMs      0.928x   (-7.2%)   <- extract hits the decode interpret cached
interpretMs    1.005x             (first decode = miss; insert overhead only)
peakRssBytes   1.008x   (+0.8%)   <- budget-bounded, negligible
open/firstPage/save                within noise
VERDICT: OK
```

Text extraction is 7.2% faster on this corpus of small docs; the win scales with
Flate `/Contents` size (dense CAD) and compounds in the editor, where hover→
extract, select→elements, and re-render on zoom all re-decode the same content.
Rendering is byte-unchanged (Ghent render baselines identical - the cache is
transparent). `decoded_cache_test.dart` pins the contract: same-buffer hit,
`stopBeforeFilter` keying, new-object miss (immutability), the item cap, and LRU
eviction to budget.
