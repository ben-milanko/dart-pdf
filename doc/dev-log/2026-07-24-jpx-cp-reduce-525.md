# 2026-07-24 — JPX resolution-level skip (cp_reduce), #525

Continued the #520 PDFium comparative study into the deferred deep tier. Landed
**#525** (PR #561): the JPX decoder now skips resolution levels for a
small-displayed image instead of fully decoding every megapixel and throwing
most of it away in the downsample. This is PDFium's `cp_reduce`
(`CJPX_Decoder::Init` sets `parameters_.cp_reduce`; OpenJPEG
`resolution_levels_to_skip`).

## What changed

- **`packages/pdf_cos/lib/src/filters/jpx.dart`** — `JpxDecoder.decode` gains
  `reduceLevels`. The parser resolves an effective reduce (`_effectiveReduce`,
  applied only when every component decomposes to the same level count so the
  MCT and plane geometry stay dimension-aligned; clamped to the depth), stores
  it as `_reduce`, and:
  - `reconstruct([reduce])` keeps resolutions r0..keptR (`keptR = levels -
    reduce`): it neither runs tier-1 (MQ) decode on the finest N resolutions'
    code blocks — the dominant cost — nor performs their inverse-wavelet
    synthesis step.
  - `_decodeTile` places each tile component at its **kept** resolution's
    geometry, and `decode()` sizes the output planes to the reduced canvas
    (`_ceilDivPow2`). `reduce == 0` collapses all of this to the original
    full-size arithmetic, byte-for-byte.
  - **Tier-2 is untouched**: every packet is still parsed, so the bitstream
    stays in sync. This is the safe way to capture the win without touching the
    delicate progression/packet reader — the skipped work is entirely the
    expensive entropy decode + IDWT, not the cheap header walk.

- **`packages/pdf_graphics/lib/src/image_pixels.dart`** — `_decodeJpxScaled`
  hooks the scaled-decode façade (`decodePdfImagePixelsScaled`): for a plain
  (colour, unmasked, non-Indexed) JPX shown at least 2× smaller than native it
  computes `reduce = floor(log2(min(w/tw, h/th)))`, decodes reduced, then
  box-filters the already-small raster to the exact target. Indexed and masked
  JPX fall back to a full decode — a reduced index/luminance plane would be
  *wrong* there, not merely slower. The worker's decode-to-display cap
  (`render_command_codec` `_targetDecodedSize` → `decodePdfImage(targetWidth:,
  targetHeight:)`) already drives this, so the win lands on exactly the path
  that matters: a big JPX drawn small.

## Measured

2048×2048 JPX (`opj_compress`), median of 7, VM decode:

| reduce | output | lossy (629 KB) | lossless (4.3 MB) |
|-------:|:------:|:--------------:|:-----------------:|
| 0 (full) | 2048² | 1018 ms (baseline) | 2451 ms (baseline) |
| 1 | 1024² | 0.226x (4.4×) | 0.288x |
| 2 | 512²  | **0.062x (16×)** | 0.068x |
| 3 | 256²  | **0.020x (50×)** | 0.017x |

Matches the issue's "16–64× less decode when 2–3 levels dropped." Peak RSS
drops in step — the native-size RGBA buffer is never materialized (complements
#437, which caps the *post*-decode buffer).

**Fidelity**: each reduced decode is within **2/255 mean-abs-error** of a
box-downsample of the full image. Expected — the wavelet LL band *is* an
antialiased downsample, so `reduce N` is a valid low-resolution reconstruction,
exactly as PDFium/OpenJPEG accept it. `reduce 0` is bit-identical.

## Measurement note (for next time)

The reduce only manifests on the **decode-to-display** path, which the
NullDevice VM sweep (`tool/perf.sh diff`) never exercises — it decodes at native
resolution. So the honest measurement here is a **decoder microbenchmark** on a
real large JPX (`opj_compress` local; `gen_ppm.dart` + `bench_jpx.dart` in the
session scratchpad), not a `tool/perf.sh` scenario. An end-to-end number would
need a flutter-render scenario that rasterizes a JPX-heavy page at a small
display size — filed thought for a follow-up; the raw-decode microbenchmark is
the correct and sufficient evidence for a codec-internal change.

## The remaining deep tier (scoped, not landed)

#525 was the last self-contained, cleanly-measurable win of the study. The
remaining four are architectural and interactive-render-loop bound:

- **#526** base-raster viewport cull — the region-index/grid machinery
  (`region_replay_index.dart`, `retained_scene.dart`) already culls, but only
  for the deep-zoom **detail** patch; the base raster does a full-transcript
  replay (`_replayOnto` with `rasterRegion == null`). Extending the cull to the
  base is a real trade: the base raster is currently **scale-independent and
  pannable-in-place** (the cached image transform-scales during pan without
  re-render), so a viewport-culled base would need pan/scroll invalidation — a
  pan-responsiveness regression surface. And at fit-to-page (the default) the
  whole page is in-viewport, so there is *nothing to cull*; the win is narrow
  (scrolled into a dense page mid-document) and overlaps the detail path.
  Needs a `tool/perf.sh webdiff` cad scenario to justify before landing.
- **#527** progressive reveal / **#530** resume-from-object — share a resumable
  render-cursor primitive and are best done together; perceived-latency wins
  that are hard to put a throughput number on.

These are the "measure first, don't rush" tier: each wants a dedicated design +
Chrome-harness measurement loop rather than a speculative push.
