# 2026-07-16 - Release 1.4.6 (packages, all app platforms, site)

Cut and shipped 1.4.6 end to end: 7 packages to pub.dev, the app to all six
platforms plus both stores, and the marketing site.

## What shipped

- **pub.dev**: all 7 packages at 1.4.6, published via the manual path
  (`tool/release.sh --publish --yes`). The automated OIDC pipeline is still
  blocked on the two maintainer config gaps - see `doc/RELEASING-packages.md`.
- **App**: `app-v1.4.6` -> `release-app.yml` built all six platforms green; the
  draft GitHub Release was reviewed and published (the in-app update checker
  needs it non-draft to see it through the unauthenticated `/releases` API).

- **Site**: `firebase deploy` from `site/` published `sdk.html` (the SEO /

## Changelog gap worth knowing about

Only two packages had `## Unreleased` sections, but five had real code changes
since 1.4.5. `pdf_graphics` (Arabic tashkil clustering, BiDi-control-stripping
in `findAll`, scaled CCITT/1-bit-gray decode), `pdf_test_fixtures` (positioned
tashkil fixture) and `dart_pdf_editor` (remote-apply undo checkpoints, DejaVu +
platform Arabic fallbacks, regenerated web worker) would all have shipped under
a false "no API changes since 1.4.5" version-bump line. **Diff `lib/` per package
against the previous tag before writing changelogs** - don't trust `Unreleased`
to be complete:

```
git diff --name-only pdf_cos-v1.4.5..HEAD -- packages/<pkg>/lib packages/<pkg>/assets
```

## `tool/release.sh` hangs on a stalled curl

`pub_has_version()` calls `curl -fsSL` with **no `--max-time`**. A pub.dev
connection stalled mid-run and the curl never returned, so `wait_for_pub`'s
60x10s cap never applied - the loop was blocked *inside* the check rather than in
`sleep`, and the release would have hung forever.

Diagnosing it: `release.sh` alive, no `pub publish` child, log frozen. Note the
log lags ~4KB behind regardless (the progress dots are block-buffered through the
`tee`/pipe), so a stale log is **not** itself evidence of a hang. The tell is
`pgrep -P <pid> -l` showing a `curl` child with a large `etimes`. Killing that
curl lets the loop self-recover: python gets EOF, `pub_has_version` returns 1, and
the next iteration retries.

Fix worth making: `--max-time 30` on that curl. Until then, consider a watchdog
for the run.

## Other traps hit

- `pub publish --dry-run` exits non-zero on *warnings*, and `release.sh` is
  `set -euo pipefail` - so an uncommitted tree stops the dry run at the first
  package. Commit the version bump first, then dry-run.
- `google_play_upload.sh` needs `--aab` as an **absolute** path (it `cd`s to
  `app/`, so `app/build/...` becomes `app/app/build/...`).
- Its `--key` must be a real file (`[[ -f ]]` test, then read twice), so process
  substitution can't be used to avoid materializing the service-account key.
- `flutter build ipa` rewrites `app/ios/Podfile.lock` with the local CocoaPods
  version (1.16.2 -> 1.17.0) while spec checksums stay identical. Incidental
  toolchain churn - revert it rather than committing it.
